# gov-skills data lakehouse

Terraform for a data lakehouse pipeline built for a South African government skills-development
client. It replicates tables out of a client-owned Azure MySQL server, lands them in S3, and
transforms them through a layered lakehouse into Kimball-style dimension and fact tables — both
queryable in place as Iceberg and mirrored into Postgres for downstream BI/reporting. Two Step
Functions state machines, backed by nine Lambdas, orchestrate the whole thing end to end.

Everything here is infrastructure-as-code; there is no application code. Region: AWS `af-south-1`.

## Architecture

![Architecture: Azure MySQL replicates via DMS into S3 raw/, a Glue crawler catalogs it, Glue ETL cleans it into S3 curated/, builds SCD2 dims and Kimball facts in S3 layer2/ as Iceberg tables, then publishes them to RDS Postgres — orchestrated by two Step Functions state machines, dms-raw and src-improved-pipeline.](docs/architecture.svg)

Orchestration sits on top as two Step Functions state machines:

- **`dms-raw`** — archive current `raw/`, run the DMS reload, crawl `raw/`, validate the crawl,
  then invoke `src-improved-pipeline` as its last step.
- **`src-improved-pipeline`** — the nightly ETL: `curated/` build, layer2 dims, layer2 facts, then
  publish dims/facts to Postgres, in dependency order.

Nine Lambdas (`lambda/`) do the individual orchestration steps (start DMS, poll DMS status, run
the crawler, poll crawler status, validate the raw load, start/poll each Glue job, notify on
failure via SNS); the state machine definitions are Terraform-templated from
[infra/step_functions/*.asl.json.tftpl](infra/step_functions/) so Lambda ARNs and Glue job names
always match what's actually deployed rather than drifting static strings.

## Stack

- **Terraform** (AWS provider) — all infrastructure, `infra/`
- **AWS DMS** — full-load MySQL → S3 replication
- **AWS Glue** — Spark ETL jobs, Data Catalog, crawler
- **Apache Iceberg** (on S3, via Glue) — the `layer2/` warehouse (SCD2 dims, Kimball facts)
- **AWS Lambda** (Node.js 20, AWS SDK v3) — pipeline orchestration steps, `lambda/`
- **AWS Step Functions** — the two state machines described above
- **Amazon RDS for PostgreSQL** — publish target for downstream BI
- **Secrets Manager** — all runtime credentials (nothing hardcoded — see [Security](#security))

## Running it

```bash
cd infra
terraform init
terraform plan -var-file=prod.tfvars
terraform apply -var-file=prod.tfvars
```

`prod.tfvars` is gitignored (it holds `dms_source_password` in plaintext) and must exist locally —
it supplies the source DB connection details, which have no defaults. State is remote (S3 backend,
native S3 locking, Terraform >= 1.11).

An EventBridge Scheduler ([infra/schedule.tf](infra/schedule.tf)) starts `dms-raw` automatically
every night at 23:00 `Africa/Johannesburg` time — `dms-raw` cascades into `src-improved-pipeline`
as its last step, so that's the only schedule needed. Everything downstream of a reload (the
individual Glue jobs, the crawler) is still triggered manually or via the state machines rather
than on its own separate schedule. After `apply`:

1. Read the `dms_replication_instance_public_ips` output and allowlist those IPs on the source
   Azure MySQL server's firewall — Terraform can't do this, and a stuck task is almost always this.
2. The nightly schedule takes it from there; to trigger a run immediately instead of waiting for
   23:00, run `aws stepfunctions start-execution --state-machine-arn <dms_raw ARN>`.

## Security

- No credentials are hardcoded anywhere in this repo. DMS/Postgres credentials are generated by
  Terraform (`random_password`) or supplied via `prod.tfvars`/`TF_VAR_*`, stored only in Secrets
  Manager, and read by each Glue/Lambda script at runtime.
- `prod.tfvars`, `*.tfstate`, `tfplan`, and Lambda `node_modules/` are all gitignored and were
  never committed.
- [publish_postgres.tf](infra/publish_postgres.tf) documents why this matters: the original
  hand-built version of this pipeline had its Postgres password committed in plaintext across
  shared docs. This rebuild reads everything from Secrets Manager instead, and that password was
  rotated independently of this repo.

## Known limitations

- **`build_etqa_facts.py`'s join logic is an unverified placeholder.** It replaces a Glue job from
  the original hand-built pipeline whose source was never recovered; the output schema matches
  what `publish_etqa_facts_postgres.py` expects, but which source columns actually produce that
  schema hasn't been checked against real crawled data. Needs verification once `curated/`/
  `layer2/` are populated from a real reload.
- No CI — `terraform fmt`/`validate` are run locally, not enforced on push.
- No automated tests for the Glue/Lambda scripts; correctness is currently verified by running the
  pipeline manually against real data.
